1. CI/CD Integration with Gitea

Automate your Terraform deployments using a CI/CD pipeline. This section walks you through setting up a local Gitea instance, pushing your Terraform files, and triggering automatic infrastructure updates on every commit.

1.1. Install Gitea locally

Gitea is a lightweight, self-hosted Git service with built-in CI/CD (Gitea Actions). Install it on your local machine: 

# Option 1: Using Docker (recommended)
docker run -d --name gitea \
  -p 3000:3000 \
  -p 2222:22 \
  -v gitea-data:/data \
  gitea/gitea:latest

# Option 2: Using binary (Linux/amd64)
wget -O gitea https://dl.gitea.com/gitea/1.22/gitea-1.22-linux-amd64
chmod +x gitea
./gitea web

# Access Gitea at http://localhost:3000
# Complete the initial setup wizard (SQLite is fine for local use)

1.2. Install Gitea Act Runner (for CI/CD)

Gitea Actions requires a runner to execute your pipelines. Install and register one: 

# Download the act runner
wget -O act_runner https://dl.gitea.com/act_runner/0.2/act_runner-0.2-linux-amd64
chmod +x act_runner

# Register the runner with your Gitea instance
# Get the registration token from: Site Administration > Runners > Create new Runner
./act_runner register --instance http://localhost:3000 --token YOUR_REGISTRATION_TOKEN

# Start the runner (runs in foreground)
./act_runner daemon

1.3. Create a repository and push Terraform files

Create a new repository in Gitea, then push your Terraform configuration files: 

# Create a new repo in Gitea UI: http://localhost:3000/repo/create
# Name it: openstack-infra

# Initialize your local project and push
cd terraform/
git init
git remote add origin http://localhost:3000/your-user/openstack-infra.git

# Copy the terraform files into the repo
cp main.tf variables.tf outputs.tf versions.tf terraform.tfvars.example .

# Create the CI workflow directory
mkdir -p .gitea/workflows/

1.4. Create the CI/CD pipeline file

Create the pipeline definition that Gitea Actions will execute on every push: 

# .gitea/workflows/deploy.yaml
name: Terraform Deploy

on:
  push:
    branches: [main]
    paths:
      - '*.tf'
      - '*.tfvars'

env:
  OS_AUTH_URL: ${{ secrets.OS_AUTH_URL }}
  OS_APPLICATION_CREDENTIAL_ID: ${{ secrets.OS_APPLICATION_CREDENTIAL_ID }}
  OS_APPLICATION_CREDENTIAL_SECRET: ${{ secrets.OS_APPLICATION_CREDENTIAL_SECRET }}
  OS_PROJECT_NAME: ${{ secrets.OS_TENANT_NAME }}
  OS_REGION_NAME: ${{ secrets.OS_REGION_NAME }}
  TF_VAR_student_id: ${{ secrets.STUDENT_ID }}
  TF_VAR_student_password: ${{ secrets.STUDENT_PASSWORD }}
  TF_VAR_instance_flavor: ${{ vars.INSTANCE_FLAVOR }}
  TF_VAR_instance_image: ${{ vars.INSTANCE_IMAGE }}
  TF_VAR_network_name: ${{ secrets.STUDENT_ID }}-private-network
  TF_VAR_key_name: opcp-openstack-automation-ssh-key

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
      - name: Terraform Init
        run: terraform init
      - name: Terraform Validate
        run: terraform validate

  plan:
    runs-on: ubuntu-latest
    needs: validate
    steps:
      - uses: actions/checkout@v4
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
      - name: Terraform Init
        run: terraform init
      - name: Terraform Plan
        run: terraform plan -out=tfplan
      - name: Upload Plan
        uses: actions/upload-artifact@v4
        with:
          name: tfplan
          path: tfplan

  deploy:
    runs-on: ubuntu-latest
    needs: plan
    environment: production
    steps:
      - uses: actions/checkout@v4
      - name: Setup Terraform
        uses: hashicorp/setup-terraform@v3
      - name: Download Plan
        uses: actions/download-artifact@v4
        with:
          name: tfplan
      - name: Terraform Init
        run: terraform init
      - name: Terraform Apply
        run: terraform apply -auto-approve tfplan

1.5. Configure secrets in Gitea

Store your OpenStack credentials as repository secrets so they are available to the pipeline without being exposed in code: 

# In Gitea UI: Repository > Settings > Actions > Secrets
# Add the following secrets:
#   OS_AUTH_URL                      → your OpenStack auth URL
#   OS_APPLICATION_CREDENTIAL_ID    → your credential ID
#   OS_APPLICATION_CREDENTIAL_SECRET → your credential secret
#   OS_TENANT_NAME                  → your project/tenant name
#   OS_REGION_NAME                  → your region
#   STUDENT_ID                      → your student identifier
#   STUDENT_PASSWORD                → your instance user password
#
# Add the following variables (Settings > Actions > Variables):
#   INSTANCE_FLAVOR                 → e.g. scale-1
#   INSTANCE_IMAGE                  → e.g. Debian 12 LVM OPCP

1.6. Commit and push to trigger the pipeline

Push your files to the main branch. The pipeline will trigger automatically: 

# Add all files and push
git add .
git commit -m "Initial Terraform infrastructure"
git push -u origin main

# The pipeline runs: validate → plan → deploy
# Monitor progress at: http://localhost:3000/your-user/openstack-infra/actions

1.7. Modify Terraform to trigger an update

To test the full CI/CD cycle, make a change to your Terraform configuration and push. For example, increase the instance count: 

# Edit a terraform file — e.g. change instance_count
sed -i 's/instance_count = 1/instance_count = 2/' terraform.tfvars

# Commit and push the change
git add terraform.tfvars
git commit -m "Scale up: 2 instances"
git push

# The pipeline detects the .tf/.tfvars change and runs again:
#   validate → plan (shows +1 instance) → deploy (creates the new instance)

💡 Tips:

  • The paths filter in the workflow ensures the pipeline only runs when *.tf or *.tfvars files change.
  • Use the environment: production setting to add manual approval before deploy if desired.
  • Keep terraform.tfstate in .gitignore — state should not be version-controlled. For team use, configure a remote backend.
  • You can replace hashicorp/setup-terraform with opentofu/setup-opentofu to use OpenTofu instead.
  • The pipeline uses -auto-approve on apply because the plan was already reviewed in the plan stage.

2. Best Practices

  • Never hard-code credentials — use environment variables or application credentials.
  • Validate before deploying — catch CIDR, port, and reference errors early.
  • Use version control — track every config change in Git.
  • Tag resources — metadata makes cost allocation and cleanup easier.
  • Automate teardown — always have a cleanup path to avoid orphaned resources.
  • Monitor deployments — log deployment IDs and durations for observability.
  • Rotate credentials — use short-lived application credentials and rotate regularly.

3. SDK vs Terraform vs Ansible

Each approach has strengths. Choose based on your team's workflow.

Aspect OpenStack SDK Terraform Ansible
Language Python HCL YAML
Paradigm Imperative Declarative Declarative / Procedural
State management Manual Built-in state file Stateless (idempotent)
Rollback Custom (DeploymentEngine) terraform destroy / tofu destroy Manual / playbook
Best for Complex logic, dynamic configs Reproducible infra, team workflows Config management, multi-step provisioning 
# Quick comparison — deploy the same stack three ways

# SDK
python tests/deploy_example.py

# Terraform
cd terraform && terraform apply -auto-approve
# Or, with OpenTofu:
cd terraform && tofu apply -auto-approve

# Ansible (when playbooks are ready)
ansible-playbook ansible/playbook.yml -e @vars.yml

Summary

  • Deploy to multiple regions for redundancy with a simple loop or provider aliases.
  • Integrate with CI/CD — validate, plan, then apply with manual approval.
  • Build reusable modules to standardize common patterns.
  • Choose the right tool: SDK for flexibility, Terraform for state management, Ansible for configuration.
