1. CI/CD Integration with Gitea & OpenTofu

In this section, you will set up a complete local CI/CD pipeline using Gitea (a self-hosted Git forge) and OpenTofu. The goal: when you modify a parameter in your source file (e.g. change the instance flavor or image), push the change to Gitea, and the pipeline automatically runs tofu apply to create or update your compute instance on OpenStack.

1.1. Scenario overview

Here is the workflow we will build:

  1. You have an OpenTofu file (main.tf) that defines a simple compute instance on OpenStack.
  2. Instance parameters (flavor, image, name) are stored in a separate terraform.tfvars file.
  3. You push everything to a local Gitea repository.
  4. When you modify terraform.tfvars (e.g. change instance_flavor from "scale-1" to "scale-2") and push, Gitea Actions automatically triggers a pipeline that runs tofu plan then tofu apply.
  5. OpenStack provisions or updates the compute instance according to the new parameter.

1.2. Install Gitea locally

Gitea is a lightweight, self-hosted Git service with built-in CI/CD (Gitea Actions). Install it on your local machine: 

# Option 1: Using Docker (recommended)
docker run -d --name gitea \
  -p 3000:3000 \
  -p 2222:22 \
  -v gitea-data:/data \
  gitea/gitea:latest

# Option 2: Using binary (Linux/amd64)
wget -O gitea https://dl.gitea.com/gitea/1.22/gitea-1.22-linux-amd64
chmod +x gitea
./gitea web

1.4. Write the OpenTofu configuration

Create a minimal OpenTofu project that deploys a single compute instance. This is the infrastructure-as-code that the CI/CD pipeline will manage. 

# versions.tf — Provider requirements
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~> 2.0"
    }
  }
}

provider "openstack" {
  # Credentials come from environment variables set by the CI pipeline:
  # OS_AUTH_URL, OS_APPLICATION_CREDENTIAL_ID, OS_APPLICATION_CREDENTIAL_SECRET
}
# variables.tf — Input parameters (values provided by terraform.tfvars)
variable "instance_name" {
  description = "Name of the compute instance"
  type        = string
}

variable "instance_flavor" {
  description = "Flavor (size) of the instance — e.g. scale-1, scale-2"
  type        = string
}

variable "instance_image" {
  description = "Image to boot from — e.g. Debian 12 LVM OPCP"
  type        = string
}

variable "network_name" {
  description = "Name of the private network to attach"
  type        = string
}

variable "key_name" {
  description = "SSH key pair name"
  type        = string
}
# main.tf — The compute instance resource
resource "openstack_compute_instance_v2" "app_server" {
  name        = var.instance_name
  flavor_name = var.instance_flavor
  image_name  = var.instance_image
  key_pair    = var.key_name

  network {
    name = var.network_name
  }
}

output "instance_ip" {
  description = "Private IP address of the instance"
  value       = openstack_compute_instance_v2.app_server.access_ip_v4
}
# terraform.tfvars — Parameters you modify to trigger changes
instance_name   = "my-app-server"
instance_flavor = "scale-1"
instance_image  = "Debian 12 LVM OPCP"
network_name    = "student01-private-network"
key_name        = "opcp-openstack-automation-ssh-key"

1.5. Create the Gitea repository and push

Create a new repository in Gitea and push the OpenTofu project: 

# Create a new repo in Gitea UI: http://localhost:3000/repo/create
# Name it: openstack-infra

# Initialize your local project
mkdir openstack-infra && cd openstack-infra
git init

# Add the OpenTofu files
# (versions.tf, variables.tf, main.tf, terraform.tfvars created above)

# Create a .gitignore to exclude state files
cat > .gitignore <<EOF
.terraform/
*.tfstate
*.tfstate.backup
.terraform.lock.hcl
EOF

# Create the CI workflow directory
mkdir -p .gitea/workflows/

# Connect to Gitea and push
git remote add origin http://localhost:3000/your-user/openstack-infra.git
git add .
git commit -m "Initial OpenTofu infrastructure"
git push -u origin main

1.6. Create the CI/CD pipeline

This is the key file. It tells Gitea Actions to run tofu plan and tofu apply whenever a .tf or .tfvars file is modified on the main branch: 

# .gitea/workflows/deploy.yaml
name: OpenTofu Deploy

on:
  push:
    branches: [main]
    paths:
      - '*.tf'
      - '*.tfvars'

env:
  OS_AUTH_URL: ${{ secrets.OS_AUTH_URL }}
  OS_APPLICATION_CREDENTIAL_ID: ${{ secrets.OS_APPLICATION_CREDENTIAL_ID }}
  OS_APPLICATION_CREDENTIAL_SECRET: ${{ secrets.OS_APPLICATION_CREDENTIAL_SECRET }}
  OS_AUTH_TYPE: "v3applicationcredential"

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Install OpenTofu
        uses: opentofu/setup-opentofu@v1

      - name: Initialize OpenTofu
        run: tofu init

      - name: Validate configuration
        run: tofu validate

      - name: Plan changes
        run: tofu plan -out=tfplan

      - name: Apply changes
        run: tofu apply -auto-approve tfplan

1.7. Configure secrets in Gitea

Store your OpenStack credentials as repository secrets so the pipeline can authenticate without exposing credentials in code: 

# In Gitea UI: Repository > Settings > Actions > Secrets
# Add the following secrets:
#
#   OS_AUTH_URL                       → your OpenStack auth URL
#                                       (e.g. https://auth.cloud.ovh.net/v3)
#   OS_APPLICATION_CREDENTIAL_ID     → your application credential ID
#   OS_APPLICATION_CREDENTIAL_SECRET  → your application credential secret

1.8. Trigger the automation — modify a parameter

Now the full loop is in place. To demonstrate the automation, simply change a parameter in terraform.tfvars and push: 

# Example: change the instance flavor from scale-1 to scale-2
sed -i 's/instance_flavor = "scale-1"/instance_flavor = "scale-2"/' terraform.tfvars

# Commit and push the change
git add terraform.tfvars
git commit -m "Change flavor to scale-2"
git push

# Gitea detects the .tfvars change and triggers the pipeline:
#   1. tofu init      — downloads the OpenStack provider
#   2. tofu validate  — checks syntax
#   3. tofu plan      — shows: ~ openstack_compute_instance_v2.app_server (flavor change)
#   4. tofu apply     — recreates the instance with the new flavor
#
# Monitor the run at: http://localhost:3000/your-user/openstack-infra/actions

You can modify any parameter in terraform.tfvars — instance name, image, network — and the pipeline will automatically reconcile the infrastructure to match. This is the power of declarative IaC combined with CI/CD: your Git repository becomes the single source of truth for your infrastructure.

💡 Tips:

  • The paths filter in the workflow ensures the pipeline only runs when *.tf or *.tfvars files change — editing a README won't trigger a deploy.
  • Add an environment: production block on the deploy job to require manual approval before applying.
  • Keep terraform.tfstate in .gitignore — for team use, configure a remote backend (S3, Swift, etc.).
  • The pipeline uses -auto-approve because the plan was already generated and saved as an artifact in the same run.
  • For safety, you can split into two jobs: one for plan (on any branch) and one for apply (only on main after review).

2. Best Practices

  • Never hard-code credentials — use environment variables or application credentials.
  • Validate before deploying — catch CIDR, port, and reference errors early.
  • Use version control — track every config change in Git.
  • Tag resources — metadata makes cost allocation and cleanup easier.
  • Automate teardown — always have a cleanup path to avoid orphaned resources.
  • Monitor deployments — log deployment IDs and durations for observability.
  • Rotate credentials — use short-lived application credentials and rotate regularly.

3. SDK vs Terraform vs Ansible

Each approach has strengths. Choose based on your team's workflow.

Aspect OpenStack SDK Terraform Ansible
Language Python HCL YAML
Paradigm Imperative Declarative Declarative / Procedural
State management Manual Built-in state file Stateless (idempotent)
Rollback Custom (DeploymentEngine) terraform destroy / tofu destroy Manual / playbook
Best for Complex logic, dynamic configs Reproducible infra, team workflows Config management, multi-step provisioning 
# Quick comparison — deploy the same stack three ways

# SDK
python tests/deploy_example.py

# Terraform / OpenTofu
cd terraform && tofu apply -auto-approve

# Ansible (when playbooks are ready)
ansible-playbook ansible/playbook.yml -e @vars.yml

Summary

  • Integrate with CI/CD using Gitea & OpenTofu — set up a local Git forge, push your .tf files, and any parameter change in terraform.tfvars triggers automatic infrastructure deployment.
  • Follow best practices — never hard-code credentials, validate early, tag resources, and automate cleanup.
  • Choose the right tool: SDK for flexibility, Terraform/OpenTofu for state management, Ansible for configuration.
