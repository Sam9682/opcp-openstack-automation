1. Intégration CI/CD avec Gitea & OpenTofu

Dans cette section, vous allez mettre en place un pipeline CI/CD local complet avec Gitea (une forge Git auto-hébergée) et OpenTofu. L'objectif : lorsque vous modifiez un paramètre dans votre fichier source (ex. changer le flavor ou l'image de l'instance), vous poussez le changement vers Gitea, et le pipeline exécute automatiquement tofu apply pour créer ou mettre à jour votre instance compute sur OpenStack.

1.1. Vue d'ensemble du scénario

Voici le workflow que nous allons construire :

  1. Vous disposez d'un fichier OpenTofu (main.tf) qui définit une instance compute simple sur OpenStack.
  2. Les paramètres de l'instance (flavor, image, nom) sont stockés dans un fichier séparé terraform.tfvars.
  3. Vous poussez le tout vers un dépôt Gitea local.
  4. Lorsque vous modifiez terraform.tfvars (ex. changez instance_flavor de "scale-1" à "scale-2") et poussez, Gitea Actions déclenche automatiquement un pipeline qui exécute tofu plan puis tofu apply.
  5. OpenStack provisionne ou met à jour l'instance compute selon le nouveau paramètre.

1.2. Installer Gitea localement

Gitea est un service Git léger et auto-hébergé avec CI/CD intégré (Gitea Actions). Installez-le sur votre machine locale : 

# Option 1 : Avec Docker (recommandé)
docker run -d --name gitea \
  -p 3000:3000 \
  -p 2222:22 \
  -v gitea-data:/data \
  gitea/gitea:latest

# Option 2 : Avec le binaire (Linux/amd64)
wget -O gitea https://dl.gitea.com/gitea/1.22/gitea-1.22-linux-amd64
chmod +x gitea
./gitea web
  • Accédez à Gitea sur http://localhost:3000
  • Complétez l'assistant d'installation (SQLite suffit pour un usage local)

1.3. Installer Gitea Act Runner (pour le CI/CD)

Gitea Actions nécessite un runner pour exécuter vos pipelines. Installez et enregistrez-en un : 

# Télécharger le runner
wget -O act_runner https://dl.gitea.com/act_runner/0.2.0/act_runner-0.2.0-linux-amd64
chmod +x act_runner

Enregistrez le runner auprès de votre instance Gitea. Récupérez le token depuis : Administration du site > Runners > Créer un nouveau Runner

./act_runner register --instance http://localhost:3000 --token VOTRE_TOKEN

# Démarrer le runner (s'exécute au premier plan)
./act_runner daemon

1.4. Écrire la configuration OpenTofu

Créez un projet OpenTofu minimal qui déploie une seule instance compute. C'est l'infrastructure-as-code que le pipeline CI/CD va gérer. 

# versions.tf — Exigences du provider
terraform {
  required_version = ">= 1.6.0"
  required_providers {
    openstack = {
      source  = "terraform-provider-openstack/openstack"
      version = "~> 2.0"
    }
  }
}

provider "openstack" {
  # Les identifiants proviennent des variables d'environnement définies par le pipeline CI :
  # OS_AUTH_URL, OS_APPLICATION_CREDENTIAL_ID, OS_APPLICATION_CREDENTIAL_SECRET
}
# variables.tf — Paramètres d'entrée (valeurs fournies par terraform.tfvars)
variable "instance_name" {
  description = "Nom de l'instance compute"
  type        = string
}

variable "instance_flavor" {
  description = "Flavor (taille) de l'instance — ex. scale-1, scale-2"
  type        = string
}

variable "instance_image" {
  description = "Image de démarrage — ex. Debian 12 LVM OPCP"
  type        = string
}

variable "network_name" {
  description = "Nom du réseau privé à attacher"
  type        = string
}

variable "key_name" {
  description = "Nom de la paire de clés SSH"
  type        = string
}
# main.tf — La ressource instance compute
resource "openstack_compute_instance_v2" "app_server" {
  name        = var.instance_name
  flavor_name = var.instance_flavor
  image_name  = var.instance_image
  key_pair    = var.key_name

  network {
    name = var.network_name
  }
}

output "instance_ip" {
  description = "Adresse IP privée de l'instance"
  value       = openstack_compute_instance_v2.app_server.access_ip_v4
}
# terraform.tfvars — Paramètres que vous modifiez pour déclencher des changements
instance_name   = "my-app-server"
instance_flavor = "scale-1"
instance_image  = "Debian 12 LVM OPCP"
network_name    = "student01-private-network"
key_name        = "opcp-openstack-automation-ssh-key"

1.5. Créer le dépôt Gitea et pousser

Créez un nouveau dépôt dans l'interface Gitea : http://localhost:3000 (nommez-le "openstack-infra") et poussez le projet OpenTofu : 

# Initialisez votre projet local
mkdir openstack-infra && cd openstack-infra
git init
git checkout -b main

Ajoutez les fichiers OpenTofu (versions.tf, variables.tf, main.tf, terraform.tfvars créés ci-dessus) 

# Créez un .gitignore pour exclure les fichiers d'état
cat > .gitignore <<EOF
.terraform/
*.tfstate
*.tfstate.backup
.terraform.lock.hcl
EOF

# Créez le répertoire du workflow CI
mkdir -p .gitea/workflows/

# Connectez-vous à Gitea et poussez
git remote add origin http://localhost:3000/votre-utilisateur/openstack-infra.git
git add .
git commit -m "Infrastructure OpenTofu initiale"
git push -u origin main

1.6. Créer le pipeline CI/CD

Voici le fichier clé. Il indique à Gitea Actions d'exécuter tofu plan et tofu apply à chaque fois qu'un fichier .tf ou .tfvars est modifié sur la branche main : 

# .gitea/workflows/deploy.yaml
name: OpenTofu Deploy

on:
  push:
    branches: [main]
    paths:
      - '*.tf'
      - '*.tfvars'

env:
  OS_AUTH_URL: ${{ secrets.OS_AUTH_URL }}
  OS_APPLICATION_CREDENTIAL_ID: ${{ secrets.OS_APPLICATION_CREDENTIAL_ID }}
  OS_APPLICATION_CREDENTIAL_SECRET: ${{ secrets.OS_APPLICATION_CREDENTIAL_SECRET }}
  OS_AUTH_TYPE: "v3applicationcredential"

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Install OpenTofu
        uses: opentofu/setup-opentofu@v1

      - name: Initialize OpenTofu
        run: tofu init

      - name: Validate configuration
        run: tofu validate

      - name: Plan changes
        run: tofu plan -out=tfplan

      - name: Apply changes
        run: tofu apply -auto-approve tfplan

1.7. Configurer les secrets dans Gitea

Stockez vos identifiants OpenStack comme secrets du dépôt pour que le pipeline puisse s'authentifier sans exposer les identifiants dans le code : 

# Dans l'interface Gitea : Dépôt > Paramètres > Actions > Secrets
# Ajoutez les secrets suivants :
#
#   OS_AUTH_URL                       → votre URL d'authentification OpenStack
#                                       (ex. https://auth.cloud.ovh.net/v3)
#   OS_APPLICATION_CREDENTIAL_ID     → votre ID d'identifiant d'application
#   OS_APPLICATION_CREDENTIAL_SECRET  → votre secret d'identifiant d'application

1.8. Déclencher l'automatisation — modifier un paramètre

La boucle complète est maintenant en place. Pour démontrer l'automatisation, modifiez simplement un paramètre dans terraform.tfvars et poussez : 

# Exemple : changer le flavor de l'instance de scale-1 à scale-2
sed -i 's/instance_flavor = "scale-1"/instance_flavor = "scale-2"/' terraform.tfvars

# Committer et pousser le changement
git add terraform.tfvars
git commit -m "Changement de flavor vers scale-2"
git push

# Gitea détecte le changement .tfvars et déclenche le pipeline :
#   1. tofu init      — télécharge le provider OpenStack
#   2. tofu validate  — vérifie la syntaxe
#   3. tofu plan      — affiche : ~ openstack_compute_instance_v2.app_server (changement de flavor)
#   4. tofu apply     — recrée l'instance avec le nouveau flavor
#
# Suivez l'exécution sur : http://localhost:3000/votre-utilisateur/openstack-infra/actions

Vous pouvez modifier n'importe quel paramètre dans terraform.tfvars — nom de l'instance, image, réseau — et le pipeline réconciliera automatiquement l'infrastructure. C'est la puissance de l'IaC déclaratif combiné au CI/CD : votre dépôt Git devient la source unique de vérité pour votre infrastructure.

💡 Conseils :

  • Le filtre paths dans le workflow garantit que le pipeline ne s'exécute que lorsque des fichiers *.tf ou *.tfvars changent — modifier un README ne déclenchera pas de déploiement.
  • Ajoutez un bloc environment: production sur le job deploy pour exiger une approbation manuelle avant l'application.
  • Gardez terraform.tfstate dans .gitignore — pour un usage en équipe, configurez un backend distant (S3, Swift, etc.).
  • Le pipeline utilise -auto-approve car le plan a déjà été généré et sauvegardé comme artefact dans la même exécution.
  • Pour plus de sécurité, vous pouvez séparer en deux jobs : un pour plan (sur toute branche) et un pour apply (uniquement sur main après revue).

2. Bonnes pratiques

  • Ne jamais coder les identifiants en dur — utilisez des variables d'environnement ou des identifiants d'application.
  • Valider avant de déployer — détectez les erreurs de CIDR, ports et références tôt.
  • Utiliser le contrôle de version — suivez chaque changement de configuration dans Git.
  • Taguer les ressources — les métadonnées facilitent l'allocation des coûts et le nettoyage.
  • Automatiser le démontage — ayez toujours un chemin de nettoyage pour éviter les ressources orphelines.
  • Surveiller les déploiements — journalisez les IDs et durées de déploiement pour l'observabilité.
  • Rotation des identifiants — utilisez des identifiants d'application à durée limitée et effectuez une rotation régulière.

3. SDK vs Terraform vs Ansible

Chaque approche a ses forces. Choisissez en fonction du workflow de votre équipe.

Aspect OpenStack SDK Terraform Ansible
Langage Python HCL YAML
Paradigme Impératif Déclaratif Déclaratif / Procédural
Gestion de l'état Manuelle Fichier d'état intégré Sans état (idempotent)
Rollback Personnalisé (DeploymentEngine) terraform destroy / tofu destroy Manuel / playbook
Idéal pour Logique complexe, configs dynamiques Infra reproductible, workflows d'équipe Gestion de config, provisionnement multi-étapes 
# Comparaison rapide — déployer la même pile de trois façons

# SDK
python tests/deploy_example.py

# Terraform / OpenTofu
cd terraform && tofu apply -auto-approve

# Ansible (quand les playbooks sont prêts)
ansible-playbook ansible/playbook.yml -e @vars.yml

Résumé

  • Intégrez avec le CI/CD via Gitea & OpenTofu — installez une forge Git locale, poussez vos fichiers .tf, et toute modification de paramètre dans terraform.tfvars déclenche automatiquement le déploiement de l'infrastructure.
  • Suivez les bonnes pratiques — ne jamais coder les identifiants en dur, valider tôt, taguer les ressources, et automatiser le nettoyage.
  • Choisissez le bon outil : SDK pour la flexibilité, Terraform/OpenTofu pour la gestion d'état, Ansible pour la configuration.
